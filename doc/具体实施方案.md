## 3.1 巡线与感知方案（定稿）

### 3.1.1 控制架构

- 采用 **FSM 状态机** 作为整体控制主干。
- 状态：`WAIT_START → TRACKING → ZEBRA_STOP → TRAFFIC_LIGHT → AVOID_CONE → PARKING → DONE`
- 每个状态独立调试，用录播回放复盘。

### 3.1.2 巡线方案

- **正常赛道**：OpenCV 扫线求中线，作为主力方案；
- **模型职责（v2.0）**：**元素检测模型**只识别特殊元素（挡板、斑马线、红绿灯、锥桶、停车区），回答"是什么/在哪"，由 FSM 解读成事件；**不负责每帧分割跑道**。路面理解交给独立的**语义分割模型**；
- **异常兜底链路**：
  ```text
  OpenCV 置信度正常
    → 信任 OpenCV center_x

  OpenCV 置信度低（连续 N 帧）
    → 降低油门
    → 使用最近一次 RKNN 结果（若新鲜度 <100ms 且包含车道/分割信息）

  RKNN 也没有有效车道
    → 使用上一帧有效 center_x + IMU 航向短时维持 0.3~0.8 秒

  ＞1~1.5 秒无有效信息
    → 电调归零，安全停车
  ```
- **内道/草坪/阴影问题（v2.0 更新）**：
  - 阴影**不作为类别**，作为困难样本 + 数据增广 + 摄像头曝光控制处理；
  - **内道/草坪边界**由独立的**语义分割模型**（track / grass / white_line）兜底，输出与扫线同构的 center_x；
  - 数据从 P5 起**随车存帧**（零成本），标注延后到「决策门」评估后再决定；分割模型成熟可转为常开甚至转正，扫线退化为快速校验。

### 3.1.3 数据集要求

**元素检测（YOLO11n-det）— 8 类**（下表）：

| 类别 | 说明 |
|---|---|
| blue_board | 蓝板（停车区遮挡判定用；**发车挡板不走模型**，见 §3.1.7） |
| crosswalk | 斑马线 |
| traffic_light_off | 红绿灯灭灯（**必须标，防止误判为绿灯抢跑**） |
| traffic_light_red | 红灯 |
| traffic_light_green | 绿灯 |
| obstacle_cone_blue | 蓝色锥桶 |
| obstacle_cone_red | 红色锥桶 |
| parking_area | 整个黄胶布长方形停车区（**标一个框，不分成两格**，见 §3.1.9） |

> **变更（v2.0）**：**发车挡板**不再作为检测类别，改为**画面遮挡检测 + 边沿触发**（见 §3.1.7）；**停车区**改为检测 `blue_board`（蓝板）+ `parking_area`（黄色胶布区域），由 FSM 判断哪一侧未被遮挡（见 §3.1.8）。原"停车标志位-左/右"类别取消——左右属于**空间关系**，做成类别标签会被 `fliplr` 翻转增广破坏，且要求模型看到完整场景，泛化差。（现有 Roboflow 标注框可原地复用，只需改类别名。）

**语义分割（轻量模型）— 3 类**

| 类别 | 说明 |
|---|---|
| track | 可行驶赛道（含红/蓝跑道段） |
| grass | 草坪 / 内道 |
| white_line | 白色边界线 |

> 阴影**不进类别表**，作为困难样本 + 增广 + 曝光控制处理；遮挡物不推断。详见 §5.7。

### 3.1.4 仲裁层 `vision/lane_arbiter.py`（v2.0 新增）

扫线通道（A）与分割通道（C）**输出同构观测量** `center_x + confidence`，由仲裁层统一调度：

| 条件 | 动作 |
|---|---|
| A 置信度正常 | 采用 A.center_x |
| A 置信度低（连续 N 帧） | 降油门，尝试 C（要求新鲜度 <100ms 且 valid） |
| C 也无有效中心线 | 上一帧有效 center_x + IMU 航向短时维持 0.3~0.8s |
| > 1~1.5s 仍无有效信息 | 电调归零，安全停车 |

- A 通道置信度指标：有效扫描点数 / 左右边界拟合残差 / 线宽一致性。
- 该层必须是**独立模块 + 单元测试**，不得散落在 `postprocess.py` 里。
- C 通道成熟后可转为常开、甚至转正，A 退化为快速校验。

### 3.1.5 红绿灯专项方案（v2.0 新增）

**规则要点**：赛事方在距红绿灯 1m 处（跑道右/左侧）放置光敏传感器 → 小车经过触发 → 灯变红 → 小车停车等待 → 绿灯亮起后通过。

**（1）光敏传感器**
- 现购（官方淘宝店）传感器仅 20cm 内可触发，不满足 1m 要求，**必须更换**。
- 推荐 E18-D80NK 红外光电开关（3~80cm 可调、数字量输出、抗环境光），或光敏模块 + LM393 可调比较器 + 遮光筒；**阈值必须现场可调**（比赛场地光照不可控）。
- **必须加超时兜底**：若未收到触发信号，状态机仍需在规定时间后按保守策略处置，避免死锁。

**（2）摄像头与云台**
- 红绿灯横置于离地 **40cm** 架子上；下摄在近距离看不到，**只能用云台摄像头**。
- 先确认相机索引：`ls /dev/video*` + `v4l2-ctl --list-devices`，再逐路抓帧肉眼确认。
- 在 `ZEBRA_STOP → TRAFFIC_LIGHT` 切换时就**抬头到预设角度**，按距离分 2~3 档标定；不用连续视觉伺服（复杂且抖动）。
- **双摄分时复用**：巡线期用下摄，`TRAFFIC_LIGHT` 状态切云台摄，避免两路同时推理。
- 优势：等待绿灯时车辆**静止**，可低频（5 FPS）+ 多帧累积 + 轻微扫视提高检出率。

**（3）类别与标注**
- 类别：`traffic_light_off` / `traffic_light_red` / `traffic_light_green`。**灭灯必须标**——否则模型会把灭灯误判为绿灯导致抢跑。
- 采集方式：**录视频**，覆盖"灭 → 红 → 绿"完整周期，再抽帧标注；**不要拍单张照片**。
- 采集矩阵：距离 5m / 3m / 2m / 1m × 光照 正午强光 / 黄昏 / 阴影，每档 3~5 段。
- 每类 ≥200 实例；**红→绿过渡帧单独保留**，不得丢弃。

**（4）时序决策（禁止单帧决策）**
- 等待绿灯：**连续 5 帧**判定 green 且置信度 > 阈值，才允许起步；
- 红灯判定：连续 3 帧即可（保守策略）；
- 灭灯 / 不确定：维持停车；
- 超时 T（建议 45~60s）后按规则条款保守处置，并记录日志。

### 3.1.6 算力预算

- RK3588 NPU 为共享资源，两个模型**分频运行**：元素检测 10~15 FPS（优先保障锥桶避障 <80ms 链路），路面分割 5~10 FPS 起步。
- 分割模型需单独准备 10~50 张真实赛道图做 INT8 校准。
- 双摄按 FSM 状态分时复用，不做两路同时推理。

### 3.1.7 发车信号：遮挡检测（v2.0 新增）

**规则**：发车区有一块蓝色挡板挡在车头前，挡板被移除 = 发车信号。**不使用模型检测。**

| 判据 | 说明 |
|---|---|
| 颜色占比 | HSV 蓝色像素占比 > 阈值（近距离挡板几乎占满画面） |
| 画质退化 | 拉普拉斯方差 / 边缘密度骤降（挡板贴近镜头导致大面积失焦） |
| 帧间突变 | 挡板被移走瞬间帧差剧增 |

- ⚠️ **必须边沿触发**：只有"有遮挡 → 无遮挡"的**跳变沿**才算发车信号；**绝不能用"当前无遮挡"直接发车**，否则一上电就冲出去。
- 状态机：`WAIT_START` 持续检测 → 先确认"遮挡存在"→ 再等"遮挡消失"的跳变 → `TRACKING`。
- 跳变后需**连续 N 帧（如 5 帧）**均判定无遮挡才真正发车（去抖）。
- 阈值**现场可调**；调试窗口实时显示蓝色占比 / 边缘密度数值。
- 优点：零标注、零算力、不依赖模型（挡板贴在镜头前，检测框根本框不住）。

### 3.1.8 停车区判定：蓝板 + 黄色胶布区域（v2.0 新增）

**规则**：场地有上下（或左右）两个停车区，裁判随机用**一块蓝板**遮住其中一个；小车必须停进**未被遮挡**的那个，且**四轮入区**。

**摄像头可见内容**：蓝板 + 黄色胶布围起来的区域 → 因此模型只需检测这两样。

**感知输出**：`parking_area`（1~2 个框）、`blue_board`（0~1 个框）

**FSM 判定逻辑**：

```text
检测到 2 个 parking_area
  → 选【没有被 blue_board 覆盖】的那个
     （用蓝板中心是否落在区域内判断，比 IoU 更稳）

检测到 1 个 parking_area
  → 若它被 blue_board 覆盖 → 判定"另一个没被挡"，需位置先验或低速搜索
  → 若它没被覆盖           → 直接选它

检测到 0 个 parking_area
  → 低速前进 + 搜索；超时后按安全策略处置
```

- 停车成败判据是**四轮入区**，属控制问题：用 `parking_area` 的框中心/底边作为目标点，低速视觉伺服接近。
- 黄色胶布颜色鲜明，可用 **HSV 阈值做二次校验**（模型 + 传统 CV 双确认），防止强光/阴影下误判。
- 近距离时蓝板会盖住停车区的一部分，必须用"蓝板中心落在哪个框内"而非重叠面积。

### 3.1.9 停车区判定：几何先验法（v2.3 重写）

> **为什么要重写**：v2.2 依赖"被挡车位的黄框是否可见"做分支判断，
> 但**裁判的放法完全不可预测**（板可能放在格内、压在中线胶布上、盖住整段胶布），
> 这个分支**根本没法提前确定**。必须换成**不依赖黄框可见性**的方案。

**核心思路：把不确定性从"感知"搬到"几何"**

> **唯一需要检测的语义只有一件事：蓝板在哪。**
> 车位布局是**固定的、已知的**，不需要靠检测得到。

**四个步骤**

1. **标注改成"整个大长方形一个框"**：`parking_area` = 整个黄胶布长方形（**一个实例**，不分成两格）。
   理由：中间分割线可能被蓝板完全盖住，标两格不可靠；**外框最大、最稳**。
2. **中间分割线用几何推算，不靠检测**：分割线 = 外框的**水平中点**（必须在俯视图里算）。
3. **用 IPM（逆透视变换）消除透视误差** ⚠️ 关键，不能省。
   - 摄像头安装固定 + 地面平坦 → **一个固定的单应矩阵**即可把画面转成俯视图。
   - **不做 IPM 会判错**：斜视角下图像里"大框的中点"**不等于**地面真实中点（近处放大、远处压缩），直接用图像中点会把分割线判偏。
4. **用蓝板"接地点"判定**：
   - 蓝板**底边中点** → IPM → 俯视图坐标 `board_x`；
   - `board_x` 在外框中点左侧 → 左格被挡 → **停右半格**；反之停左半格；
   - 目标点 = 空闲半格的几何中心（同样在俯视图里算）。

**为什么这套不怕裁判怎么放**

| 裁判的放法 | 影响 |
|---|---|
| 板放在格内 | ✅ 不影响 |
| 板压在中间黄线上 | ✅ 不影响 |
| 板盖住整段中间胶布 | ✅ 不影响（中线是**算出来**的，不是看出来的） |
| 板盖住半个外框 | ✅ 外框另一半仍在，配合已知宽度先验可用 |
| 板盖住**整个**停车区 | ❌ 极端情况 → 走降级链 |

**降级链**

| 能看到什么 | 怎么判 |
|---|---|
| **外框 + 蓝板** | IPM 后按左右半判定 ✅ **主路径** |
| 只有一侧外框边 | 用已知车位宽度先验补出另一侧 |
| 只有一个完整车位框、框内无蓝板 | 该框就是空的 → 停它 |
| 框内**有**蓝板 | 该框被挡 → 取镜像的另一半 |
| 蓝板接地点落在中线附近（±容差） | 用蓝板**底边的横向占用范围**判断主要压在哪侧；仍不确定则回溯更远距离的那一帧 |
| 黄胶布完全不可见 | 低速前进搜索；超时保守停车 |

**与精调链路的衔接**

```text
远距：模型 + IPM  → 判定 → 锁定目标半格（俯视坐标）
近距：HSV 找黄线  → 横向对准该半格（不需要重新判断哪格是空的）
纵向：黄线 y 位置 + 里程 → 四轮入区
```

> ❓ **待确认的几何前提**：两个格子相对小车是**左右并排**还是**前后排列**？
> 左右并排 → 比 `board_x` 与中点；前后排列 → 比 `board_y`，且需在接近过程中连续判断。

> ↓↓↓ 以下为 v2.2 旧方案（保留备查）↓↓↓

> **修订说明**：原方案假设"始终能看到两个车位"，据此设计了"蓝板落点 → 判定 → 选另一个"。
> 实际情况是**裁判站在赛道上用蓝板挡住其中一个车位，小车始终只看到 1 个车位 + 1 块蓝板**。
> 因此必须先搞清"歧义到底会不会发生"，再决定用哪套逻辑 —— **不要靠推演，要实测**。

**[旧] 第一步：现场 10 分钟验证**

摆好真实场地 → 裁判按比赛方式遮挡 → 小车停在**进入停车区的决策距离（3~5m）** → 抓一张照，回答三个问题：

1. 画面里能看到**几个**车位黄框？完整还是部分？
2. 蓝板的**底边中点**落在这个黄框的**里面还是外面**？
3. 被挡的那个车位，黄框**还能不能看到**？

**[旧] 第二步：按实测结果选逻辑**

| 现场实际画面 | 判定逻辑 | 复杂度 |
|---|---|---|
| 蓝板**完全不在**可见车位框内 | 可见车位是**空的** → 直接停它 | 最低 ✅ |
| 被挡车位的黄框**完全不可见**（被裁判身体/蓝板挡住） | 可见车位 = 空车位 → 直接停它 | 最低 ✅ |
| 可见的 1 个车位框**内有**蓝板 | 该车位**被挡** → 需找另一个（见第三步） | 高 |
| 两个车位框**都能看到** | 蓝板落点 → 选另一个（原方案，最清晰） | 中 |

**[旧] 第三步：用跑道约束**

| 车位排布 | 约束方式 |
|---|---|
| **沿赛道前后排列** | 车位在赛道上的位置固定 → 用**里程 + 车位顺序**判断"看到的是第几个"，另一个在前方 X 米 |
| **左右并排** | 用可见车位框在画面中的**横向位置** + 蓝板相对车位的**左右关系**推断另一个在左还是右 |
| **兜底** | 低速前进一小段，让另一个车位进入视野后再判定（牺牲一点时间换可靠性） |

> ⚠️ 之所以会"分不清"，根因是**蓝板是竖立的**：它在图像里会**向上延伸**，
> 几何中心可能透视上压在更远处车位的影像区域内。
> 因此落点判定**必须用底边中点（接地线）**，而不是几何中心。


**场地实况**：停车区是一整块**黄色胶布围成的长方形**，中间用黄胶布再分隔成**两个车位**；裁判用**蓝板抵住**其中一个车位。

**① 决策要"早"（仅当实测落在上表第 ③/④ 行时才需要）**

- 在 **3~5m** 能看到完整车位布局时**一次性决策**，锁定目标车位；
- 锁定后**不再重新判断**，避免靠近后视野变窄导致误判。

> **"分不清"的根因**：小车靠近后视野只剩一个车位时，若画面里是「1 个车位 + 1 块蓝板」，
> 而**蓝板被挡住的那个车位的黄框是否可见**又不确定，就无法区分"被挡的那个"还是"没被挡的那个"。

**② 蓝板落点判定：用"底边中点"，不是几何中心**

- 蓝板是**竖着抵在车位里**的，在图像中会向上延伸；
- 用几何中心判断会**偏高**，可能正好压在中间那条黄线上导致误判；
- **必须用蓝板框的底边中点（接地线）**做落点判定。

**③ 靠近与入位：模型管"选哪个"，传统 CV 管"怎么停"**

| 阶段 | 手段 | 理由 |
|---|---|---|
| 选出车位 | **模型**（`parking_area` + `blue_board`） | 语义判断，模型更稳 |
| 横向对准（中远距） | 模型框中心 → 横向偏差 | 距离远，黄线太细，HSV 不稳 |
| 横向对准（近距离） | **OpenCV HSV 黄线检测**（限定画面下方 ROI） | 黄胶布颜色纯、对比强，HSV 又快又稳；模型在近距离大目标上反而容易出框抖动 |
| 纵向定位 | 黄线在图像中的 **y 位置** + 里程/时间 | 进区后黄线会从画面底部消失 |
| 入区判定（四轮入区） | 里程计数 + 黄线位置 | 摄像头看不到自己的车轮 |

- **不要全程依赖模型精调**：模型输出是"框"，抖动大、频率低；精停阶段需要 30Hz 以上的连续控制量，HSV + ROI 能每帧输出。
- ROI **只在 `PARKING` 状态启用**，避免赛道上其它黄色物体干扰。
- 黄胶布 HSV 阈值**现场标定**（光照差异大）。

### 3.1.10 双模型 / 线程划分 / 算力分配（v2.0 补充）

**确认：2 个模型，分开训练、分开部署**

| 模型 | 任务 | 目标频率 | 说明 |
|---|---|---|---|
| 元素检测 | YOLO11n-det，8 类 | **15~30 FPS** | 锥桶 / 斑马线 / 红绿灯（灭→红→绿全过程）/ 蓝板 / 停车区 |
| 路面分割 | 语义分割，3 类 | 5~10 FPS | 扫线失效时兜底，条件触发 |

**vision 进程内的线程划分**

```text
T0 采集线程      摄像头取流（双摄分时复用）→ 只保留最新帧
T1 扫线线程      OpenCV 每帧跑（轻量）→ center_x + confidence
T2 检测线程      YOLO11n-det，15~30 FPS
T3 分割线程      语义分割，5~10 FPS（常开或按需）
T4 仲裁/发布线程  lane_arbiter + 组装观测量 → 控制进程
```

- ⚠️ **NPU 是共享资源**，T2 / T3 会互相抢核，必须显式隔离：
  - 方案 A：**RKNN core mask 隔离**（检测用 core 0，分割用 core 1）；
  - 方案 B：**单一推理线程 + 任务队列**，两模型排队使用 NPU（实现简单，**推荐先用 B**）。
- **不要让两个线程无条件并发调 RKNN**，否则总吞吐可能反而下降。
- **控制环不受模型频率限制**：扫线通道每帧跑，控制环可维持 30~50Hz；检测模型只提供离散事件（"看到锥桶"），15~30 FPS 完全够用。

### 3.1.11 性能目标与"是否转 C++"的判断依据（v2.0 补充）

**先纠正一个认知**：10~15 FPS 是**全链路**（采集→推理→后处理→仲裁→进程间通信→控制）的保守工程值，**不是 RK3588 NPU 的推理上限**。

**瓶颈通常不在 NPU，而在下面这些地方**：

| 瓶颈 | 说明 | 优化手段 |
|---|---|---|
| Python 后处理 | NMS / 解码 / RKNN 输出解析 | 用 RKNN 内置后处理、C++ 化、numpy 向量化 |
| 进程间通信 | UDP + JSON 序列化，开销与抖动 | 合并进程，或改共享内存 |
| 图像前处理 | resize / 颜色空间转换 | C++/OpenCV 优化，或直接喂 NPU 输入格式 |
| NPU 争抢 | 两个模型并发 | core mask 隔离 / 统一调度 |
| GIL | Python 多线程实际近似串行 | 关键路径 C++ 化，或 multiprocessing |

**推荐演进路线（不要一上来就整体重写）**：

```text
第 1 步  保留 Python 双进程 + UDP（调试期最方便）
第 2 步  【T2 阶段就做基准测试】测出：单帧纯推理耗时 / 后处理耗时 / 端到端 FPS
第 3 步  按数据优化热点：
         - 后处理是瓶颈 → C++ 化后处理（性价比最高）
         - 通信是瓶颈   → 合并进程 / 共享内存
         - NPU 是瓶颈   → core mask + 降输入分辨率 + 精简模型
第 4 步  以上都做完仍不达标，才考虑整体 C++ 重写
```

- **降输入分辨率是最快的手段**：640 → 480 通常明显提速，但会牺牲远距离小目标（锥桶）召回，需实测量化权衡。
- **阶段性目标**：先达成「检测 ≥15 FPS、端到端延迟 <80ms」，跑通后再冲 ≥30 FPS。
- ⚠️ **竞速真正怕的不是"帧率低"，而是"误检"**：误检 → 误刹车 / 误停车，才是最大的时间黑洞。**先保误检率，再提帧率。**






## 3.2 调试工具与 X11 说明

### 3.2.1 X11 是什么？和图传有关吗？

- **X11 转发** 是 SSH 的一个功能：把远程 Linux 上的 GUI 窗口显示到你本地电脑屏幕上。
- 它只用于本地调试，比如在香橙派上运行 OpenCV `imshow` 弹出实时画面窗口时，通过 MobaXterm/X11 在电脑上看。
- **和比赛图传无关**。比赛图传是摄像头画面通过 ffmpeg/WebRTC 推到官方网页，浏览器观看。
- 如果不开 X11，程序里有 `imshow` 会报错或看不到窗口；可以改成“不弹窗、直接保存图片/打印数值”的方式。

### 3.2.2 camera_save.cpp 能否用来采集训练数据？

可以。

- `camera_save.cpp` 本质是调用摄像头拍照并保存图片，适合采集停车标志物、锥桶、红绿灯、赛道等训练图片。
- 注意：
  1. 运行前先停 ffmpeg 推流服务，否则摄像头被占用；
  2. 采集完恢复推流；
  3. 如果不开 X11，建议改造成无窗口批量保存，或直接写一个 Python 采集脚本，更方便批量命名和按类别归档。
- 参考：`视频讲解与word实验文档/摄像头使用模块/摄像头功能使用实验.md`、`避障停车/避障停车实验.md`。

### 3.2.3 IMU 传感器实验有什么用？

- IMU 实验用于读取 JY901S 九轴姿态数据（加速度、陀螺仪、角度）。
- 在比赛中的用途：
  - **巡线丢失时短时航向保持**：视觉丢失后靠 IMU yaw 维持方向几秒；
  - **弯道辅助**：配合视觉判断急弯；
  - **姿态/侧倾监测**：防止状态异常。
- 它不是巡线的必需品，但作为“视觉丢失兜底”和状态机稳定性增强，建议接入。

### 5.3 训练与部署要点

- 元素检测使用 **YOLO11n-det**（目标检测），路面理解使用**独立的轻量语义分割模型**；不采用 YOLO11-seg，不采用 YOLOv5；
- 训练尺寸统一 640×640；
- 最终部署 RKNN INT8，需要准备 10~50 张真实场景校准图片；
- 如果 INT8 精度不足，使用混合量化或退回 FP16；
- 部署目标 15~25 FPS（Python + INT8 + 线程池）。

### 5.4 数据采集规范（v2.0 修正）

**现有采集方式（把目标放小车附近、用手推动小车、重复几次）的问题**：

| 问题 | 后果 |
|---|---|
| 全是近距离大目标 | 实际部署需要在 **3~8m** 就发现目标，模型在远距离小目标上会失效 |
| 同一场景重复推几次 | 8 个"片段"实际是 8 次近乎相同的场景，泛化差，换场地就挂 |
| 手推速度不均匀、易糊 | 与电机驱动的速度/振动分布不符，也未采集到运动模糊等真实退化 |
| 只有正样本 | 缺少"画面里什么都没有"的负样本 → **误检率高** |
| 丢失"接近 → 通过"的完整时序 | 抽帧只拿到片段，无法覆盖决策全过程 |

**修正为：录制视频 + 抽帧标注（优先用小车自己跑）**

- 用**遥控模式让小车自己跑着录**（最贴近部署分布：速度、振动、曝光一致），或手机录像；
- 每个采集回合录**完整过程**，之后按 **1~2 秒抽 1 帧**标注；
- 必须覆盖的采集矩阵：

```text
距离：  1 / 2 / 3 / 5 / 8 m           ← 现在缺远距离
横向：  目标在画面 左 / 中 / 右 / 边缘  ← 现在基本居中
光照：  正午 / 黄昏 / 阴影 / 逆光       ← 现在单一
个体：  不同锥桶、不同挡板              ← 别只用同一个道具
负样本：无目标的纯赛道帧 ≥ 15%          ← 现在完全没有
```

- 采集策略：**操场拍摄优先，小场景为辅**；一次出车尽量采全。

### 5.5 标注规范（Roboflow）

- Roboflow **支持** `blue_barrier` + `parking_zone` 这类普通检测框类别；导出选择 **YOLO TXT (Detection)**。
- 现有"停车标志位-左/右"标注**不必重标**，在 Roboflow 里**改类别 / 合并类别**即可（改前先备份一个 version）。
- ⚠️ **禁止在 Roboflow 里做 train/val/test 划分**：它默认随机划分，会把连续帧拆散到训练集与验证集，导致验证集虚高。**全部标为 train，导出后本地按片段切分。**
- ⚠️ Roboflow 导出会重命名文件（`xxx_png.rf.<hash>.png`），**原始时间戳/片段信息会丢失**。必须在本地保留一份原始文件名映射，或先本地分组再上传。
- 确认账号额度：免费版对项目数/图片数有限制。

### 5.6 切分规范

- **必须按拍摄片段整组切分**，严禁按图片随机切分（相邻帧几乎相同 → 验证集虚高、实车失效）。
- 工具：`D:\5g\orangepi\train\split_dataset.py`
  - `frame_*` 文件按时间戳/序号切片段；
  - Roboflow 文件用 dHash 感知哈希把近似重复聚成一组。
- 建议比例 **8 : 1 : 1**；验证集/测试集保持**真实类别分布**，不做人工平衡。
- 测试集最好留**一整段独立录制**（不同时间/光照），才测得出泛化能力。

### 5.7 语义分割（track / grass / white_line）数据要求

| 项 | 要求 |
|---|---|
| 图像来源 | **巡线视角的下摄画面**（与实际推理输入完全一致） |
| 采集方式 | 跑车时**顺带存帧**，不要专门出车 |
| 数量 | 去重后 **300~500 张**起步（语义分割比检测省数据） |
| 抽样 | 按 **1~2 秒抽 1 张**，不需要连续帧 |
| 训练分辨率 | 320×192 |

**必须覆盖的场景**：直道 / 弯道 / 急弯、**内道边缘**（草坪紧贴白线）、**强阴影**、逆光、黄昏、**红/蓝跑道段**、斑马线附近、反光/湿滑路面、锥桶遮挡边缘。

**标注要求**：
- 工具：**X-AnyLabeling**（内置 SAM，半自动）或 CVAT / Labelme；
- **遮挡不推断**：被锥桶遮挡的像素标成遮挡物，不要脑补成 track；
- 边界一致性：白线在不同光照下标注同一厚度；
- 阴影**不是类别**，靠困难样本 + 亮度/对比度增广 + 摄像头曝光控制解决。

### 5.8 训练参数（YOLO11n-det，RTX 5070）

```bash
yolo detect train \
  data=datasets/smartcar2026/data.yaml \
  model=yolo11n.pt \
  imgsz=640 epochs=300 patience=50 batch=16 device=0 \
  optimizer=AdamW lr0=0.001 lrf=0.01 warmup_epochs=3 weight_decay=0.0005 \
  mosaic=1.0 close_mosaic=15 mixup=0.1 \
  hsv_h=0.015 hsv_s=0.7 hsv_v=0.4 \
  degrees=5 translate=0.1 scale=0.5 shear=2.0 perspective=0.0 \
  fliplr=0.0 flipud=0.0 \
  cache=ram amp=True seed=0
```

- `fliplr=0.0`：在类别表仍含左右语义时必须关闭；采用 §3.1.3 的 `blue_barrier + parking_zone` 方案后可放开为 0.5。
- 训练前执行 `yolo checks` 校验标签，并检查重复图片。
- 类别不平衡处理：**不做按张数裁剪对齐**；优先补拍少数类（停车补到 400~500 张、补齐片段数），多数类（锥桶/斑马线）按 `--stride 2~3` 抽帧降冗余，少数类做离线增广。

### 5.9 RKNN 转换与部署

**正确链路（本机/服务器本地转换，不用云端平台）**：

```text
best.pt
  → ONNX (opset=12, simplify=True, dynamic=False, nms=False)
  → RKNN-Toolkit2 (target_platform='rk3588', INT8 + dataset.txt 校准)
  → best_int8.rknn
```

- Ultralytics 平台的 `format="rknn"` 内部同样是 `pt → ONNX → RKNN`，但云端模板**无法指定校准集**；而 INT8 精度几乎完全由校准图片决定 → 改用本地转换（见 `doc/RKNN服务器转换指南.md`）。
- 校准集：10~50 张**真实赛道场景**图，可直接从 §5.7 的数据里选。
- 转换后必须做 **ONNX vs RKNN 精度对拍**；掉点严重则使用混合量化或退回 FP16。
- `dev/models/best11nseg.rknn` 为**上届 `.pt`** 经 Ultralytics 平台转换的产物，**类别与本届不符，不可使用**；仅可用于验证板子与工具链是否打通（测 FPS 基线），验证完删除。

## 9. 风险备忘

| 风险 | 应对 |
|---|---|
| 红绿灯识别不稳（倒计时随机 3~10s） | 数据用**视频**采"灭→红→绿"全过程；`traffic_light_off/red/green` 三类；连续 5 帧滤波；超时 45~60s 兜底 |
| **光敏传感器仅 20cm 触发，不满足 1m** | 必须更换（E18-D80NK 等可调光电开关）；阈值现场可调；状态机加超时兜底防死锁 |
| 红绿灯在 40cm 高、近距离下摄看不到 | 用云台摄像头 + 预设俯仰角；双摄按 FSM 状态分时复用；等待绿灯时车辆静止，可低频多帧累积 |
| **现有采集方式（手推小车、近距离）分布偏离部署场景** | 改为**遥控让小车自己跑着录像 + 抽帧**；补齐远距离/多角度/多光照/负样本矩阵（见 §5.4） |
| **连续帧泄漏导致验证集虚高** | 严禁按图片随机切分；按拍摄片段整组切分（`split_dataset.py`）；Roboflow 里不做划分 |
| 停车类只有 3~4 个片段，泛化风险高 | 优先补拍停车场景（目标 400~500 张、多片段多光照） |
| 两个模型抢 RK3588 NPU 算力 | 分频运行（检测 10~15 FPS、分割 5~10 FPS）；双摄分时复用；必要时分割降到 5 FPS |
| 锥桶随机位置撞桶(+20s/拖桶2m=失败) | 近端避障优先保"不撞"，宁可慢 |
| 手机热点不稳（遥控阶段裁判可能查"局域网"） | 比赛用手车 4G/5G 模块，非热点；日常开发热点可接受 |
| frp 隧道延迟波动 | pool_count 预连接（待批准）+ 图传以官方通道为主，官方拥塞为共同风险 |
| **供电（D4：不可改造）** | 螺丝不可拆、不装外部电源 → 软件降载：关闭无关服务、推理帧率分级（高负载降帧）、监测温度/意外重启日志；若出现掉电重启，记录触发条件并对应降载 |
| 官方图传服务器比赛当天拥塞 | 8080 通道页面/摇杆冗余 + 自建 mediamtx 兜底（已列 ADR 待办） |
