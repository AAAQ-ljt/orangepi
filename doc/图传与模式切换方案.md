`` `${location.protocol}://${window.location.host}/${streamPath}/whep` `` —— **同源**地址，
所以只要改小车 nginx 的 `proxy_pass` 目标，前端一行都不用动。

**流名**：网页默认 `streamPath = cam_car0027`、副摄 `cam_car0027_sub`

## 5. 工作模式切换（car-mode.sh）

上电默认**手动遥控**。要跑自主，在小车（或通过 SSH）敲：

```bash
bash /root/dev/scripts/car-mode.sh status              # 看当前模式/服务/进程/温度/摄像头占用
bash /root/dev/scripts/car-mode.sh auto                # 进入自动驾驶【默认 DRY-RUN，电机不动】
bash /root/dev/scripts/car-mode.sh auto --real         # 真正跑车（要输入 GO 确认）
bash /root/dev/scripts/car-mode.sh manual              # 回到手动遥控
bash /root/dev/scripts/car-mode.sh estop               # 紧急停止（立刻归零）
bash /root/dev/scripts/car-mode.sh stream up|down|status   # 图传推流控制
bash /root/dev/scripts/car-mode.sh logs vision|control|stream
```

`auto` 的选项：`--real`（使能动力）、`--camera N`（0=主摄/2=副摄）、`--model PATH`（RKNN 模型）、
`--max-us N`（电调上限，默认 1600；**1500 停、≈1545 才起转**）、`--port N`、`--minimal`（连网页/另一路推流也停，省 CPU）、`--yes`（跳过确认）。

**这个脚本替你保证了四件事**（旧脚本的坑都补上了）：

1. **进前体检**：python 依赖、摄像头存在且空闲、PCA9685 在线（非 dry-run 时）、UDP 端口空闲、媒体服务器可达性；
2. **只停必须停的服务**：抢 PCA9685 的 `opi-control`、占音频的 `talk-player`、**占用我们要用那路摄像头的推流**；
   **另一路推流保留**，裁判仍能看到画面（规则要求全程回传）；
3. **任何退出路径都恢复手动模式**：正常结束、Ctrl+C、SSH 断线（SIGHUP）都会触发同一个 `cleanup`，
   不会把车留在"既没遥控也没自驾"的中间态；若媒体服务器不可达，会跳过两个推流服务，避免 3 秒一次的重启循环；
4. **视觉没起来就不放行**：等视觉写出 `/tmp/smartcar_status.json`（说明真出帧了）才启动控制进程。

模式判定（`status`）：
- `control.pid` 活着 → **自动驾驶中**
- 否则 `opi-control` active → **手动遥控**

### 7.1 图传延迟定位：主摄音频那路的 512 队列（2026-10-17 实锤）

**现象**：主摄画面比实际操作慢约 2s，副摄明显更低。

**定位方法**（车端，不需要摄像头之外的设备）：
`dev/scripts/diag/stream_lag.py` —— 把 ffmpeg 进度行的 `time=` 与进程启动时刻
（`/proc/<pid>/stat` 的 starttime）相减，得到「采集→编码」滞后。改前主摄稳定 **~1.8s**。

**根因**：主摄是**唯一带音频输入**的那路（`-f alsa -i hw:3,0`），而音频输入用的是
`-thread_queue_size 512`（512 个 Opus 包 × 20ms ≈ 最长 10s 的缓冲）。AGENTS.md §6 早就写过
「**512 是延迟水库**」，但 2026-10-11 只把**视频**那路从 512 改成 16，**音频这路没改** ——
它会把同一 muxer 里的视频一起压住。

**修复**：把主摄音频那路整个关掉（`-f alsa` + `-c:a libopus` + 音频的 `-thread_queue_size 512`
三行）。车端「采集→编码」滞后 **1.8s → 0.7s**，30 分钟监测稳定不涨（副摄不受影响）。
服务文件已入库：`dev/scripts/net/ffmpeg-stream.service`；原始版本备份在车端
`/root/dev/backup-20261017/ffmpeg-stream.service.orig-20261017`。

**要恢复音频**：删掉 ExecStart 里三条 `# [AUDIO-OFF 2026-10-17]` 注释，并在行尾补回续行反斜杠
（`systemctl daemon-reload && systemctl restart ffmpeg-stream.service`）。
**想「音频和低延迟都要」**：把音频的 `-thread_queue_size` 改成 **16**（不要再用 512）——
这条**还没实测**，要做就按 §7.1 的方法量前后对比。

**量延迟的口径**：浏览器 `getStats()` 的 `estimatedPlayoutTimestamp` 会把车端排队算进去，
**不能直接当端到端**（它对音频实测比声学闭环高约 1s）；最可靠的是「秒表放镜头前，比视频里显示的时间」。

## 8. 网络故障恢复（2026-09-16 实战复盘）

**现象**：小车重启后 WiFi 与流量卡都连不上、frp 隧道掉线、SSH 全部失联。

**诊断结论（三条）**：

1. **蜂窝其实一直是好的**——由 `/etc/rc.local` 调用的**官方 `simcom-cm`**
   （`/root/SIM8200_for_RPI/Goonline/`）负责拨号。
   团队后加的 `car-dial.service`（跑 `/root/car_net_up.sh`，用 qmicli 手拨）
   **从来没成功过**（日志里 `OK IP=` 计数为 0），而且它每次都会 `ip addr flush dev wwan0`
   并抢 QMI 设备，**把官方拨号已建立的连接打断**——表现就是"流量卡连不上"。
   → **处置：`systemctl disable --now car-dial.service`**（脚本保留；
   真需要手动拨号时先确认 simcom-cm 没在跑，再 `bash /root/car_net_up.sh`）。
2. **WiFi**：`Aaaq` 热点重启后卡在 activating / connecting(getting IP configuration)；
   `nmcli con down Aaaq && nmcli con up Aaaq` 后恢复正常（关联成功、拿到地址）。
3. **网络全断时唯一入口 = 串口**：CH340 → `COM8` / **1500000** / 8N1。
   用 `python scripts/serial_car.py "命令"` 免交互操作（自动登录 + 标记捕获），
   详见 AGENTS.md §4.2。

**恢复顺序（照这个顺序做，最快）**：
```text
串口能进 → 看 wwan0 有没有 IP（ip -4 a show wwan0）
        → 有 IP 但连不通：查默认路由（ip r）与 dns（resolvectl status）
        → 没有 IP：确认 simcom-cm/rc.local 是否执行；必要时手动拨号
        → 网络通后看隧道：systemctl status frpc-ssh（应有 start proxy success）
        → 页面：http://121.40.149.155:8080/
```

**安全组现状（2026-09-16）**：已放行 `7000` `8080` `8554` `8889` `8189(TCP/UDP)` `8888`；
**待补**：`80`（域名 `liyekai380.dpdns.org` 裸域名入口）、`22`（服务器自身 SSH）、`2222`（小车 SSH 隧道）。

### 9.3 手柄按钮的接管原理与还原

官方按钮是 `onclick="toggleGamepadControl()"`，经典脚本里 `function` 声明会挂到 `window`，所以：

1. **运行时替换 `window.toggleGamepadControl`** → 点官方按钮启动/停止**我们的**轮询
   （左摇杆X 转向 + RT 前进 / LT 倒车 + 右摇杆 云台），官方 `startGamepadLoop` **永不启动**；
2. 同时把官方 `gamepadEnabled`（`let` 全局词法绑定，只能用间接 `eval` 读写）**强制置真**，
   让官方"松手回中 / `sendDriveNow`"走它自己的 `if (gamepadEnabled) return;` 提前返回，
   **不会拿官方滑条的 0 值打掉我们的油门**；另加三层包装（`sendDriveNow`/两个 `reset*ToCenter`）做悬停保险；
3. 官方按钮文字由我们维护（官方 `updateGamepadButton()` 按它自己的 flag 写，与我们开关无关）；
4. **点【返回主页面】时把替换掉的函数、官方 flag、按钮文字原样还原**（已实测：退出后官方 `sendDriveNow`
   又能正常发帧）。所有接管点都有 `typeof` + `try/catch` 守卫，官方页改内部结构就退化成"入口按钮固定右上角 + 打日志"。

### 9.4 现场注意

- 手柄开车时**标签页必须保持前台**：轮询是 `requestAnimationFrame` 驱动的（与官方一致），
  标签页隐藏即停发手柄帧 → 后端 8s failsafe 把油门归零（**这是想要的失效方向**，但会"莫名其妙不走了"）。
- 退出驾驶模式会**先强制油门归零 + 方向回中并补发一帧**（否则藏掉面板后车会保持原油门直到 8s failsafe）。
- 油门最大值**硬钳 1600us**（AGENTS.md §1.1.3）；参数存 `localStorage["rc-drive-config"]`（与官方 `rc-ui-config` 分开）。
- 完整参数表、协议对照、耦合点清单、已知限制见 `dev/web/README.md`。
