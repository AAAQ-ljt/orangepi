# 智能车开发规范 v1.0

> 适用范围：OrangePi 5 小车代码、调试脚本、采集脚本、AI 辅助生成代码。
> 核心目标：**防止代码乱写导致摄像头被占用、电机失控、硬件资源泄漏、推流服务被破坏**。
> 所有代码在提交前必须过一遍本规范。

---

## 0. 核心原则

1. **先备份，再改动**：车端/systemd/驱动级改动必须备份原文件。
2. **谁打开，谁释放**：摄像头、PCA9685、串口、音频设备、文件资源，所有退出路径都必须释放。
3. **程序退出必须安全停车**：任何退出方式（正常、Ctrl+C、kill、崩溃回调）都要让电机归零。
4. **不碰官方服务**：除非明确批准，否则不修改官方 frpc、nginx、ffmpeg-stream 等服务和代码。
5. **可回退**：所有改动放到独立目录，例如 `/root/2026-orange-pi`，不覆盖官方演示代码。
6. **AI 生成的代码必须遵守本规范**，尤其注意资源释放和异常退出。

## 1. X11 使用规范

### 1.1 X11 是什么

- X11 转发是 SSH 的一个功能，用于把远程 Linux 的 GUI 窗口显示到本地电脑。
- 典型用途：在香橙派上运行 OpenCV `imshow()` 时，通过 MobaXterm 在电脑上查看画面。
- **X11 与比赛图传无关**，图传走的是 FFmpeg/WebRTC 推流到网页。

### 1.2 什么时候需要 X11

只有本地调试需要看实时窗口时才需要：

- OpenCV `imshow()` 预览
- GUI 调参工具
- 可视化标定

### 1.3 什么时候不应该依赖 X11

- 比赛运行程序：小车是 headless 的，不能依赖本地 GUI。
- 数据采集脚本：优先保存图片文件，而不是弹窗。
- SSH 无 X11 环境：程序里写 `imshow()` 会导致报错或卡住。

### 1.4 推荐做法

- 调试预览用宏/配置开关控制，例如：

```cpp
#ifdef SHOW_IMAGE
cv::imshow("view", frame);
cv::waitKey(1);
#endif
```

```python
if config.get("show_image", False):
    cv2.imshow("view", frame)
    cv2.waitKey(1)
```

- 正式运行/采集时关闭 `SHOW_IMAGE`，改为保存图片或只输出日志。
- 如果必须使用 X11，在 MobaXterm 中开启 X11 forwarding，并确认 `DISPLAY` 环境变量正常。

## 2. 摄像头设备占用处理

### 2.1 问题

香橙派上的 FFmpeg 推流服务会长期占用摄像头设备。如果直接打开摄像头，会报：

```text
device or resource busy
```

### 2.2 强制规则

**任何程序要打开摄像头前，必须先停止 FFmpeg 推流服务；程序退出后必须恢复。**

常用服务名：

```text
ffmpeg-stream.service
ffmpeg-stream-sub.service
```

推荐启动/停止方式：

```bash
# 停止
systemctl stop ffmpeg-stream.service
systemctl stop ffmpeg-stream-sub.service

# 启动
systemctl start ffmpeg-stream.service
systemctl start ffmpeg-stream-sub.service
```

### 2.3 代码模板

Python 使用上下文管理器，保证无论是否异常都能恢复：

```python
import subprocess
import contextlib

FFMPEG_SERVICES = [
    "ffmpeg-stream.service",
    "ffmpeg-stream-sub.service",
]

@contextlib.contextmanager
def camera_exclusive():
    try:
        for svc in FFMPEG_SERVICES:
            subprocess.run(["systemctl", "stop", svc], check=False)
        yield
    finally:
        for svc in FFMPEG_SERVICES:
            subprocess.run(["systemctl", "start", svc], check=False)

# 使用
with camera_exclusive():
    cap = cv2.VideoCapture(0)
    ...
```

C++ 中建议在 `main()` 开始和退出函数里分别执行停止/恢复，并确保退出信号回调也会恢复。

### 2.4 禁止事项

- ❌ 不停止 FFmpeg 就直接 `VideoCapture`。
- ❌ 程序崩溃后不恢复 FFmpeg，导致推流一直关闭。
- ❌ 多个程序同时抢占摄像头。
- ❌ 在采集/预览代码里硬编码 `system("pkill ffmpeg")` 这种危险命令，除非明确知道不会影响其他服务。

## 3. 安全退出机制

### 3.1 为什么重要

小车没有人工急停，如果程序被直接 `kill` 或崩溃，电机可能保持通电继续转动，非常危险。

### 3.2 强制规则

**所有退出路径都必须：**

1. 电机 PWM 归零 / 回到安全值；
2. 舵机回到中位或安全位置；
3. 释放 PCA9685；
4. 释放摄像头；
5. 恢复 FFmpeg 推流服务；
6. 释放串口/音频等其他资源。

### 3.3 信号处理

至少捕获：

```text
SIGINT   Ctrl+C
SIGTERM  kill
SIGABRT  异常终止
SIGQUIT  退出
```

Python 示例：

```python
import signal
import sys

def cleanup(signum=None, frame=None):
    print("[cleanup] stopping motor and releasing resources")
    motor.stop()
    servo.center()
    pca9685.release()
    camera.release()
    restore_ffmpeg()
    sys.exit(0)

signal.signal(signal.SIGINT, cleanup)
signal.signal(signal.SIGTERM, cleanup)
```

C++ 示例：

```cpp
void signalHandler(int signum) {
    motor.stop();
    servo.center();
    pca9685.release();
    camera.release();
    restoreFFmpeg();
    exit(0);
}

signal(SIGINT, signalHandler);
signal(SIGTERM, signalHandler);
signal(SIGABRT, signalHandler);
signal(SIGQUIT, signalHandler);
```

### 3.4 禁止事项

- ❌ 不捕获信号，直接退出。
- ❌ 退出时只 `return`，不释放硬件。
- ❌ 在信号回调里做复杂阻塞操作（如 sleep 很久、网络请求）。
- ❌ 多个退出路径各写一套释放逻辑，应该统一收敛到一个 `cleanup()`。

## 4. 低延迟摄像头设置

### 4.1 问题

OpenCV 默认摄像头缓冲会缓存多帧，导致画面延迟堆积，看起来“卡”且“慢半拍”。

### 4.2 推荐设置

Python：

```python
cap = cv2.VideoCapture(0, cv2.CAP_V4L)
cap.set(cv2.CAP_PROP_FRAME_WIDTH, 640)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 480)
cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)  # 只保留最新一帧
```

C++：

```cpp
cap.set(cv::CAP_PROP_FRAME_WIDTH, 640);
cap.set(cv::CAP_PROP_FRAME_HEIGHT, 480);
cap.set(cv::CAP_PROP_BUFFERSIZE, 1);
```

### 4.3 注意事项

- `BUFFERSIZE=1` 可能偶尔跳帧，但延迟更低，适合控制。
- 如果要做离线采集/训练数据，可以适当调大缓冲，避免丢帧。
- 正式运行时优先保证低延迟。

## 5. 音频设备处理（可选）

如果涉及语音播放/录音：

- 播放预录制语音只需要 `aplay` 或 Python `subprocess.run(["aplay", file])`。
- 如果遇到声卡被占用，先释放 pulseaudio / ffmpeg 等占用进程。
- 比赛只需要播放固定语音，**不要做实时录音和语音识别**。
- 同样遵循“用完恢复服务”的原则。

---

## 6. 并发与线程规范

- 摄像头读取、控制输出如果放在不同线程，**共享数据必须加锁**。
- 退出标志使用线程安全方式传递。
- OpenCV `waitKey()` 按键响应慢，建议用独立线程 `input()` 或信号处理来退出。
- 不要在主循环里做阻塞网络请求。
- 不要创建无法退出的后台线程。

---

## 7. 硬件资源获取/释放 Checklist

每个新程序提交前检查：

- [ ] 打开摄像头前是否停止 FFmpeg？
- [ ] 所有退出路径是否都会恢复 FFmpeg？
- [ ] 是否捕获 `SIGINT/SIGTERM/SIGABRT/SIGQUIT`？
- [ ] 退出时电机是否归零？
- [ ] 退出时舵机是否回中？
- [ ] 退出时 PCA9685 是否释放？
- [ ] 退出时摄像头是否 `release()`？
- [ ] 是否避免 `imshow()` 依赖 X11 导致 headless 运行失败？
- [ ] 是否使用 `CAP_PROP_BUFFERSIZE=1` 低延迟？
- [ ] 是否避免修改官方服务和官方代码？
- [ ] 是否有日志输出关键状态（启动、退出、异常）？

## 8. 代码结构与可维护性

推荐目录：

```text
2026-orange-pi/
├── main.py
├── config/
├── perception/
├── control/
├── hardware/
│   ├── camera.py
│   ├── pca9685.py
│   ├── motor.py
│   └── servo.py
├── teleop/
├── recorder/
├── tools/
└── tests/
```

要求：

- 硬件操作封装成类/模块，不让业务代码直接操作 GPIO/PWM。
- 摄像头独占逻辑封装成上下文管理器/RAII。
- 配置集中管理，不散落硬编码。
- 每个模块提供 mock，方便 AI 在没有真车时联调。

## 9. Git 与协作规范

- 只提交 `code/`、`doc/`、`scripts/` 内的白名单文件。
- 大文件（模型权重、视频、数据集）不入 git。
- 改动前先 `git status` 确认没有误删/误改。
- 每天收工前 push。
- 车端/systemd 重要改动必须经过队长确认。

---

## 10. AI 编码红线

AI 生成或修改代码时，**禁止**：

1. 不释放摄像头/电机/PCA9685。
2. 不停止/恢复 FFmpeg 直接操作摄像头。
3. 在正式代码里依赖 X11 弹窗。
4. 直接 `kill` 或 `systemctl disable` 官方服务。
5. 在车上执行格式化/清理命令时没有备份。
6. 写死 IP、端口、密码等敏感配置到代码里。
7. 在主循环中无退出条件的死循环。
8. 修改官方 `/root` 下的原始工程而不留备份。
9. 在没有 mock/测试的情况下直接上真车跑高风险运动代码。
10. 忽略异常，不打印日志。
