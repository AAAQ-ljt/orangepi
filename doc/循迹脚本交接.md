### 1.1 2026-09-21 本轮重构做了什么（按价值排序）

| # | 改动 | 为什么（证据） |
|---|---|---|
| 1 | **单侧丢线用「车道半宽先验」兜底**（`vision/lane_ref.py` 的 `WidthPrior` + `detect` 的单侧分支） | 复核参考实现原码发现：它丢一侧时**代画面边界照样给中心**，`newnewCode` 同款。旧版却写成"单侧不给中心"，等于把唯一能让车继续走的机制扔了 —— 这正是实跑"一动就只剩单侧 → 进不了 track"的直接原因。现在用半宽（两侧都在时实测、丢线时沿用中位数）推中心，并给**降级的质量分**让控制层降速 |
| 2 | **修「误差滤波离群阈值」的单位错误**（`scripts/lane_ref_test.py` 的 `outlier_px`） | `settings.ERROR_FILTER_OUTLIER=15` 的单位是**误差单位（1 单位 = 4px）**，旧版直接把 15 当**像素**喂给 `ErrorFilter` → 任何 >15px 的变化都被当离群点丢掉、不入队 → 滤波后误差长期卡在旧值、车对真实偏差不响应（实验室读数在 345/367 间跳时最致命）。现在按 `15 × LANE_ERROR_SCALE = 60px` 给，单测 `test_error_filter_unit_matches_pixels` 盯着 |
| 3 | **起步前自检自动化**（`_preflight`）：候选带扫描 + 自动前瞻带 + 自动目标点 + 镜头体检，一次算完并写回 `config/site.yaml` | 到操场很贵，"现场猜 ROI"猜错一次就白跑一趟。候选带表按「有中心帧数 → 支持行占比（**面积归一**，避免带越大越占便宜）→ 中心跨距」排序；前瞻带用**实测有边缘支持的行**定（不是让猜 `--band`） |
| 4 | **丢线阶梯**（`control/lane_control.py` 的 `LossGuard`）：丢线 0.6s 内沿用上次中心（误差按时间衰减回中位）+ 减速，超时停车 | 落地《具体实施方案》§3.1.4 的仲裁层设计。旧版是"没读数 → 舵角回中位/停车"，一抖就停 |
| 5 | **前瞻带与 ROI 解耦**（`look_top/bottom_ratio` 用**绝对行号比例**） | 参考实现就是这样：ROI 是 0.50~0.85，而算中心的行是 130~230，两者不重合。旧版把前瞻带做成"ROI 内的比例"，ROI 一动前瞻距离就跟着动，无法单独调 |
| 6 | **ROI 单一来源**：`LaneParams.from_settings()` 读 `settings` ← `config/site.yaml`，`lane_probe` 也用它 | 消掉旧版的"两套 ROI"缺陷（`--roi-top` 与 `LANE_ROI_TOP_RATIO` 各一份，改一处漏一处） |
| 7 | **全程落盘 + 离线复盘**：CSV 增列（滤波后误差/目标点/质量/单双侧/半宽/丢线时长），定时存原图+叠加图到会话目录，`--replay` 可换参数重算 | 本车没有 X 服务器，事后看图 + 数字是唯一途径；去一趟操场要带回"下次不用再去"的数据。`--replay` 能在笔记本上重跑检测与控制律（含打满限幅比例、方向翻转次数） |
| 8 | **Hough 角分辨率沿用 3°**（不是参考实现字面的 0.05 rad≈2.87°） | 合成图复验：同一张"线被打断 + 横纹干扰"的图，0.05 会让**整条左线消失**，3° 正常。真实赛道的线只会更碎 |
| 9 | **选带指标加「最长连续支持行」run_max**，且支持占比的分母改成"两条线都在画面内的行" | 2026-09-22 实验室实测：按原来的"支持行占比"排名时**所有候选带都只有 0~12%**（分母是整幅画面，被无关区域稀释）→ 排名等于抛硬币。改用"最长连续支持行"后，真正锁在线上那档是 **58 行**、其余 ≤20 行、旧配置与参考那档是 **0 行**，一次就分开了（见 §7） |
| 10 | **叠加图上的诊断文字改成 ASCII 短标签**（`tag`），中文的 `note` 留在 CSV 里 | `cv2.putText` 渲染不了中文：2026-09-22 存出来的叠加图上是一串 `??????`，而叠加图是本车唯一的事后看图途径 |
| 11 | **修「误差滤波在误差阶跃后永久冻结」**（`ErrorFilter` 加 `max_rejects`：连续被拒 4 次就清窗口接受新值） | 2026-09-22 落地实测（`lane_20260922_171817`）：原始误差连续 **1.3s** 在 +58~+164px，滤波后一直卡在 −29.6/+3.0 —— 车偏了十几厘米而控制器毫无反应。修复后最长冻结 **0.2s** |
| 12 | **跑偏保护同时看原始误差**（`BigErrorGuard.update(..., raw_error=)`） | 同一段数据：只盯滤波值时**跑偏保护从不触发**（原始误差连续 4s ≥40px）；修复后在 16.9s 触发停车。持续时间够长本身就能排除单帧毛刺 |
| 13 | **自检证据弱（连续支持 < 20 行）时不采纳自检出的 ROI/目标点，也不写回 site.yaml** | 2026-09-22 落地实测：车摆偏时自检把目标标成 417/291（真值约 341），车照着**错目标**跑；现在这种情况会明确提示"重新摆车"，并用 site.yaml 里的旧值。⚠️ 第一版补丁把 `weak = True` 只写进了 else 分支 → 警告打印了但目标照样被采纳（173008 那次实测），已修 + 单测盯住 |
| 14 | **跑偏保护触发时的打印不再假设"滤波后误差非空"** | 2026-09-22 落地实测崩过一次：读数质量不够（`err_c=None`）但原始误差很大 → 保护触发 → `f"{err_c:+.1f}"` 抛 `TypeError`。安全层照常执行了（finally 里电调归零/舵机回中/释放 PCA9685 都做了），但退出码变成异常。现改为 `_fmt()` 同时打印滤波后与原始误差 |
| 15 | **静止中心跨距 > 25px 也算"证据弱"**：不采纳目标点、不写回 site.yaml | 2026-09-22 实验室连跑四次，自检的『中心跨距』= 74 / 166 / 90px（车一动不动，中心却在 306/351/390 间跳，质量还是 1.00），目标点被写成 318.2 → 347.8 → 353.9 每跑一次变一次。上一版只挡了"连续支持 < 20 行"，没挡"跳中心"。好的一次（172807）跨距是 19px，不触发 |
| 16 | **前瞻带改为取『最长连续支持段』的中间 20%~80%**，不再是支持行的 15~85 分位 | 支持行的分布头尾很长（如 32~360 都有零星行），分位会把前瞻带拉宽 → 中心掺入外推行 → 静止跳动。现在只在线最连续的那一段里取中心（02530 段报告行数与跨度，< 40 行会警告） |
| 17 | **板挡太早（自检被跳过）的告警升级** | 185345 那次：板放太早 → 自检跳过 → 用旧带 + 默认目标 375 → 发车第一帧就 −115px → 跑偏保护停车。现在明确打印"自检被跳过、目标点可能不准、保护会兜住、Ctrl-C 重跑" |
| 18 | **修「不采纳目标点」形同虚设的顺序 bug** | 191511/191707/191804 实测：跨距 79/117/120/100px 时提示"不采纳"，但 `configured` 在 `params.target_ratio` 被覆盖**之后**才取值 → 还原等于没还原，目标点 352.3/389.7/260.7/344.8 照样被用并写回 site.yaml。已修（先取配置值再覆盖）+ 回归测试 `test_preflight_refuses_jittery_target` |

## 3. 运行方式（速查）

```bash
# ① 本地：只分析一张图（无需硬件；venv 里有 cv2/numpy）
cd dev && export PYTHONPATH=. && "E:/venvs/smartcar-ultra/Scripts/python.exe" \
    scripts/lane_ref_test.py --image 某张赛道图.jpg

# ② 本地：复盘一次实跑的落盘数据（换参数重跑检测 + 控制律，不用再去操场）
"E:/venvs/smartcar-ultra/Scripts/python.exe" scripts/lane_ref_test.py \
    --replay logs/lane_20260922_101500 --roi-sweep --kp 0.2 --kd 0.3

# ③ 车端：只看读数（不动电机；仍需要蓝板才算"发车"，只是不发油门）
sudo python3 /root/dev/scripts/lane_ref_test.py --no-motor --max-seconds 60

# ④ 车端：正式跑（四轮落地或架空 + 有人能立刻断电）
sudo python3 /root/dev/scripts/lane_ref_test.py --allow-motion --max-seconds 120

# ⑤ 诊断（先跑这个，看『镜头朝向体检』）
sudo python3 /root/dev/scripts/lane_probe.py --camera 2 --frames 4
```

- 摄像头固定 **`--camera 2`**（`/dev/video2` = Global Shutter = 下摄）；云台主摄（video0）不参与循迹。
- **现场操作顺序（重要）**：车摆正在车道里 → `① 先别挡板`（自检要看你前方的赛道）→
  看到 `✅ 起步前自检完成` → `② 把蓝板挡到下摄正前方` → 看到 `✅ 已确认蓝板` →
  `③ 移开板` → 发车 → `④ 再挡回板` = 立刻停（移开还能再发一次，状态会重置）。
- 跑脚本期间**两路推流会被停掉**（摄像头独占），退出自动恢复；结束后会话目录里有 CSV + 图。
- **串口上不要按 Ctrl+C**：Rockchip 内核的 FIQ Debugger 以它为触发键，会掉进 `debug>`（敲 `console` 切回）。

## 4. 算法契约

### 4.1 检测链路（`vision/lane_ref.py::LaneRefDetector.detect`）

```
ROI（y0..y1，默认取 settings ← site.yaml）
→ 灰度 → GaussianBlur(5,5,σ=0.5)
→ Canny(60,140)，**同帧自适应**：按边缘像素数把阈值往目标区间 [2000,2500] 拉，
  钳位 low∈[20,160]、high∈[40,320]
→ HoughLinesP(rho=1, theta=3°, threshold=50, minLineLength=30, maxLineGap=5)
→ 斜率先验 |dy/dx| ∈ [0.25, 2.0]（滤掉地面纹理/横向反光）
→ 按斜率符号分左右 + **位置锚定**（左线在画面中心左侧，反之亦然；锚不到的线**退回按斜率选**
  并把读数标 `anchored=False`，不是直接丢帧）
→ 每侧选一条代表线（`--pick steepest` 取 |k| 最大＝参考实现；`longest` 为备选）
→ 配对宽度闸门：两侧代表线在 ROI 中点的距离必须落在 [120,700]px，否则判"配对不可信"
→ 前瞻带（**绝对行号**，默认 look 0.35~0.48 = y 168~230）内逐行求左右交点、取中点平均 → center_x
→ error = center_x − target_px（target 由起步前自检标定）
```

**单侧丢线（本轮新增，也是与旧版最大的行为差别）**：
`center = 看到的那一侧 x ± 半宽`；半宽来自 `WidthPrior`（两侧都在时实测中位数、窗口 15 帧，
越界样本不入队），只有种子值时质量压到 0.25（低于默认阈值 → 控制层按"维持"处理）。
推出画面外的中心一律丢弃。

**质量分 quality（0~1，落进 CSV）**：
两侧成对 `1.0 × min(1, 总线段数/6)`；单侧+实测半宽 `0.55 × min(1, 该侧线段数/3)`；
单侧+种子半宽 `0.25 × …`。控制层只跟 `quality ≥ --min-quality`（默认 0.28，与 `site.yaml`
的 `arbiter_conf_thresh` 同量级）的读数走。

### 4.2 控制链路（`control/lane_control.py`）

```
error（像素）→ ErrorFilter（窗口 5 / 离群阈值 60px＝15 误差单位×4）
→ pid = kp*e + ki*∫e + kd*Δe（kp/ki/kd = 0.15/0.01/0.12，积分限幅 ±50）
→ angle = 90 + sign*pid   （sign = settings.STEER_SIGN）
→ 限幅 ±limit_deg（默认 15°）→ 输出平滑 angle = 0.7*新 + 0.3*旧
```

- `STEER_SIGN` 语义：**+1 = 角度增大是右转**（与 `control/planner.py` 同口径）。
  车上 `site.yaml` 写的是 **−1**（= 角度增大是左转），于是 `angle = 90 − pid`，等同参考实现原式。
- **2026-09-21 实测确认**：`bench_test --steer-test` 输出 90°→110°→70°→90° 时前轮"先左、后右"
  → 即"角度大=左转" → `steer_sign: -1` **是正确的**。
- 速度：基准 `--speed-us 1560`；`|e|<5` → `+speed_fast`（默认 0）；`|e|≥15` → `+speed_slow`（默认 −10）；
  **硬下限 = ESC_DEADBAND_US(1545) + 5 = 1550us**（低于死区车会从"减速"变"停车"）。

### 4.3 状态机（一帧一步）

```
gate.update(frame)  // StartGate：连续 3 帧遮挡 → 武装；武装后连续 5 帧无遮挡 → 放行
phase = stop    : 未见过板 / 板在 / 跑偏保护触发 → 电调 1500，舵机 90
phase = acquire : 已发车但**从没见过一次有效读数**且距发车 < --acquire-s(3s)：舵角回中位、电调 1560
phase = track   : 质量 ≥ --min-quality 的读数 → PID + 自适应速度
phase = hold    : 丢线但距上次有效读数 < --hold-s(0.6s)：沿用上次中心（误差按时间衰减回中位）、减速
phase = lost    : 丢线 ≥ --hold-s 或探路窗口用尽 → 停车并打印原因（结束本次行程）
跑偏保护        : |滤波后误差| ≥ 60px 连续 1.5s（--err-stop-s，0=关闭）→ 停车
行程重置        : 板再挡回来 = 停车 + 清 PID/滤波/丢线计时（移开板即可按"新行程"再发车）
```

### 4.4 与参考实现（oldCode / newnewCode）的偏离清单（**改动前必读**）

| # | 偏离 | 理由 / 依据 |
|---|---|---|
| 1 | ROI 默认取 `settings`（= `site.yaml` 现场标定），不是写死的 0.50~0.85；起步前还会扫候选带自动选 | 我们的下摄更"平"，0.50~0.85 区间里右线已出画面（2026-09-19 实测）；现场猜 ROI 代价太高 |
| 2 | 前瞻带用**绝对行号比例**（默认 0.35~0.48），参考实现是写死 130~230 行 | 参考实现本身就是"ROI 与算中心的行不重合"，旧版把它们绑在一起导致无法单独调前瞻距离 |
| 3 | 目标点用比例且**起步前自动标定**（参考写死 226/320＝它自己的安装；oldCode 内部其实是 `cols/2`） | 两套参考实现的目标点差了 132px（320 vs 452@640），说明它纯属安装相关；2026-09-21 实测"车摆正时中心 ≈346"而写死的 375 造成恒 −30px 误差 |
| 4 | 选线加**位置锚定**（左线必须在中心左侧），锚不到时退回参考实现行为并标记 | 否则会把隔壁车道/横向纹理当选（2026-09-19 实验室） |
| 5 | **单侧丢线用半宽先验**（参考实现代画面边界：【左线 x + 240】这种固定猜测） | 半宽可由实测得到，"车在自己的车道里"这条先验也永远成立；见 §1.1 第 1 条 |
| 6 | 自适应速度：默认**只减速不提速**（`--speed-fast 0`），且减速/维持档有死区下限 | 用户 2026-09-21 实测 1575us 太快；基准 1560 时 "−20" 会算出 1540 < 死区 1545 |
| 7 | Hough 角分辨率用 3°（0.0524 rad），参考实现字面是 0.05 rad | 合成图实测 0.05 会整条丢线；真实赛道线段更碎 |
| 8 | 补了参考实现**没有**的：误差滤波、丢线阶梯、跑偏保护、距离/速度估计（未做） | 参考实现单侧代边界后"没有超时兜底"，也没有任何"读数不可信"的判断 |

另外**参考实现本身的坑**（它不是教科书）：无 dt（积分/微分按帧走，隐含假设帧率固定）、
无滤波、无跑偏保护、无死区概念（那套车的电调标定未知）、泊车用 `exit(0)` 收尾不给电调中立。
移植时保留其形状，但补齐这些安全层。

### 4.5 与两个参考项目的**逐条对照**（2026-09-21 通读两个项目全部源码后补）

读的原文：`oldCode/src/vision/vision.cpp`（检测）、`oldCode/src/control/control.cpp`（控制）、
`oldCode/src/state_machine/state_machine.cpp`（怎么被调用）、`oldCode/src/motion/motion.cpp`（开环动作的

`newnewCode/src/lane_follower.py` + `config.py`（模型掩膜版的中心/误差算法）。

**关键事实（之前没人注意到）**：`oldCode` 的画面是 **320×240** ——
`launch.cpp`/`state_machine.cpp` 里写死了
`capture.set(CAP_PROP_FRAME_WIDTH, 320); capture.set(CAP_PROP_FRAME_HEIGHT, 240);`

| 环节 | 参考实现的原样（原码事实） | 我们怎么做 | 要 1:1 复现就用 |
|---|---|---|---|
| 画面 | **320×240** | 下摄 640×480 | — |

| 每侧选线 | `|k|` 最大 | 相同（`--pick steepest`，另有 `longest` 备选） | `--pick steepest` |
| **算中心的行** | **130~230**（320×240 的 **0.54~0.96**，中近处；ROI 是 0.50~0.85，两者**不重合**） | 绝对行号比例的"前瞻带"，默认 0.35~0.48，现场按**实测有边缘支持的行**自动定 | `--no-auto-look --look-top 0.542 --look-bottom 0.958` |
| 目标点 | **`frame.cols/2`**（= 画面中心；`newnewCode` 却是 226/320 —— 两套参考自己就不一致） | 起步前自动标定（车摆在车道正中时取中位），写回 `site.yaml` | `--no-auto-target --target-ratio 0.5` |
| 单侧丢线 | **代画面边界**：`l=0`（左缺）/ `r=cols`（右缺），中心 =(可见线+边界)/2 | 默认用**半宽先验**推；`border` 模式 = 参考原样 | `--single-mode border` |
| PID | `angle = 90 − (0.15·e + 0.01·∫e + 0.12·Δe)`；**按 320 宽的像素误差整定**；限幅 ±15°；输出 `0.7新+0.3旧` | 公式完全相同；增益默认 = 参考原数字，但**口径写在明面上**（见下） | `--gains literal`（默认） |

| 转向方向 | 角度**变小=右转**（`motion.cpp`：右转用 40/50、左转用 80/100/110，直行基准 80） | `steer_sign: -1` = 同口径（我们的直行基准是 90） | `--steer-sign -1` |

**`--ref-behavior` 一条命令做对照实验**：把上面"参考原样"那一列全部打开（ROI 0.50~0.85、
算中心的行 130~230、目标点 = 画面中心、单侧代画面边界、增益按画面换算、关掉自检）。
它的用途是回答一个具体问题：**"跑不出成绩，是我们的改动错了，还是镜头视角不行？"**
参考实现的镜头看得见近处地面（所以它敢用 0.54~0.96 那一段），我们的下摄太平、近处是画外 ——
所以这条 look band 在本车上多半扫不到真线（**用候选带表的『支持行占比』一看就知道**）。

**两个参考实现自己也不一致的地方**（说明这些数字都是"安装相关"，不该照抄）：

| 项 | oldCode | newnewCode |
|---|---|---|
| 画面 | 320×240 | 640×480 |
| 算中心的行 | 0.54~0.96（中近） | 权重峰值 0.31~0.43、覆盖 0.11~0.89（中远） |
| 目标点 | 画面中心 0.50 | 226/320 = **0.706** |
| 检测方式 | 纯 CV（Canny+Hough+斜率） | 模型掩膜（再走同一套"逐行中点/加权"） |

⇒ 结论：**可以照抄的是"算法形状"（斜率筛线 → 左右分组 → 选代表线 → 逐行中点 → 误差 → `90−pid`）、
不能照抄的是"数字"（ROI / 前瞻行 / 目标点 / 增益口径）** —— 这些全部跟安装与画面尺寸绑死。
本脚本因此把它们做成"起步前实测自动定 + 全部可用参数覆盖"。

#### 实测对照（2026-09-22，车端，同一张实验室实拍帧 `logs/lane_probe/frame_00.jpg`）

| 跑法 | 读数 | 判读 |
|---|---|---|
| 我们默认（ROI 0.35~0.58、前瞻 y168~230、目标 375） | 左 0 段 / 右 2 段 → 走单侧兜底：中心 164.4、质量 **0.17**（<0.28 → 按丢线处理，不跟） | **如实地说"这帧不可信"** |
| `--ref-behavior`（ROI 0.50~0.85、前瞻 y260~460、目标=画面中心） | 左 5 段 / 右 8 段 → 中心 105.7、质量 **1.00**、**锚定=False**、左线 x≈**−0.5** | **自信地给出一个错读数**：它按斜率挑到了画面最左边缘的碎边（同一张图上，参考配置"看起来"更成功，其实锁错了） |

这一条正是"参考实现在它那台车上没问题、照搬到我们这台就出问题"的机理：
它把画面下半部（我们看不见线的地方）的碎边当成车道线，然后**外推**出一个中心；
它没有任何机制能发现"这两条线底下没有边缘"。我们这边的三道闸门（位置锚定 / 配对宽度 /
质量分）就是为了把这种读数标成不可信 —— 而候选带表的『支持行占比』把它量化成一个数。

### 6.2 我（AI）给过的**错误建议**，不要照抄

1. **"参考实现单侧不给中心"** —— 错。原码对丢线的一侧代画面边界
   （`if (flagl) l = 0;` / `if (flagr) r = frame.cols;`），`newnewCode` 同款。
   照这个错误结论改出来的"单侧就丢帧"是实跑失败的直接原因之一。
2. **建议用 `--roi-top 0.55 --roi-bottom-ratio 0.9`**（想靠近参考实现的 0.50~0.85）——错。
   当前视角白线只到 y≈264，0.55~0.9 区间几乎没有白点，只会得到零星线段与 266~320 的假中心，
   实测把车带向左侧冲出赛道。
3. **把 `settings.ERROR_FILTER_OUTLIER=15` 当像素用** —— 错。它的单位是"误差单位（4px）"，
   正确值是 60px；照错的用会让滤波变成"几乎永久冻结在旧值"。
4. 早期曾判断"白线根本不在画面里"——不准确：线在画面里，只是在**上部窄带且贴边**。
5. `bench_test` 的循迹档被归档后仍留了引用（`--steer-test` 被误挡），属归档不彻底。

## 8. 改代码的红线（违反即视为严重错误，与 AGENTS.md 一致）

1. **任何可能驱动电机的操作**：默认 dry-run；必须显式 `--allow-motion`；四轮架空或场地空旷 + 有人能立刻断电。
2. **脉宽**：1500 停、**1545 死区**（1540 不转）、起步/循迹 1560、调试上限 1600；
   **任何"要让车动"的脉宽必须 > 1545**；低于死区的值必须被脚本拒绝（现已有守卫 + 单测）。
   减速/维持/限幅逻辑不许把输出压到死区以下（现已有 1550 下限 + 单测）。
3. **所有退出路径**（Ctrl-C / SIGTERM / 超时 / 异常）必须：电调归零 → 舵机回中 → 释放 PCA9685 →
   恢复 `opi-control` 与两路 `ffmpeg-stream`。信号回调里不做阻塞操作。
4. **摄像头独占**：打开前停推流、退出恢复，用 `vision/camera_guard.py`，不要手写。
5. **发车必须边沿触发**（先见板 → 再消失），绝不允许"当前无遮挡即发车"。
6. **左右不采信模型/类标签**，一律几何判定（`AGENTS.md` §6 坑表）。
7. 提交前：本地 14 个测试文件全绿 + `python -m pyflakes`（2026-09-19 就是因为没跑 pyflakes，
   把未定义变量送上台架；本轮又靠它抓住一个漏掉的 import）。提交信息写"做了什么、为什么"。
