## 1. 类别表（照主方案 §3.1.3，索引顺序即 data.yaml 顺序）

### 1.1 元素检测（YOLO11n-det，8 类）

```yaml
nc: 8
names:
  0: blue_board            # 蓝色挡板（只用于停车区遮挡判定）
  1: crosswalk             # 斑马线
  2: traffic_light_off     # 红绿灯灭灯（必须标！否则灭灯会被误判成绿灯 → 抢跑）
  3: traffic_light_red     # 红灯
  4: traffic_light_green   # 绿灯
  5: obstacle_cone_blue    # 蓝色锥桶
  6: obstacle_cone_red     # 红色锥桶
  7: parking_area          # 整个黄胶布长方形停车区（一个实例一个框，不分成两格）
```

三条容易搞错的规矩：

1. **发车挡板不进模型**——它贴在镜头前，检测框根本框不住，改用"画面遮挡检测 + 边沿触发"（主方案 §3.1.7）。模型里的 `blue_board` **只服务于停车区判定**。
2. **停车区只标外框**，中间那条分格线由**几何推算**（外框中点 / IPM），不靠检测——因为裁判的蓝板可能正好压住分格线。
3. **不做"左停车位/右停车位"这种类别**。左右是空间关系，`fliplr` 翻转增广会把标签翻错；而且要模型看全场景，泛化差。现有"停车标志位-左/右"的框**改类别名复用**即可。

### 1.2 路面语义分割（独立模型，3 类，条件触发）

```yaml
nc: 3
names: [track, grass, white_line]     # 可行驶赛道(含红/蓝跑道段) / 草坪·内道 / 白色边界线
```

- 只在「决策门 T11」判定扫线失效率偏高时才投入标注（详见 `执行路线图.md`）；
- 输入 320×192，目标 5~10 FPS，常开或按需触发；
- **阴影不作为类别**，靠困难样本 + 亮度对比度增广 + 摄像头曝光控制解决。

## 2. 数据采集规范

### 2.1 必须避开的采集方式（上届踩过的坑）

| 反模式 | 后果 |
|---|---|
| 把目标放车附近、用手推着拍 | 全是近距离大目标；实际要在 3~8m 就发现，远距离全失效 |
| 同一场景反复推几遍 | 8 个"片段"其实是同一场景，泛化差，换场地就挂 |
| 手推速度不均、容易糊 | 与电机驱动的速度/振动/曝光分布不符 |
| 只拍正样本 | 缺"画面里啥都没有"的负样本 → **误检率高**（竞速最大的时间黑洞） |
| 只拍单帧 | 丢掉"接近→通过"的完整时序，抽帧拿不到决策全过程 |

### 2.2 正确方式：录视频 + 抽帧

- **用小车自己跑着录**（遥控模式最贴近部署分布），每回合录完整过程，之后按 **1~2 秒抽 1 帧**；
- 车端工具：`dev/scripts/record_video.py`、`dev/img/camera0.sh camera2.sh`、`dev/scripts/capture_dataset.py`；
- 必须覆盖的矩阵：

```text
距离：  1 / 2 / 3 / 5 / 8 m              ← 现在缺远距离
横向：  目标在画面 左 / 中 / 右 / 边缘    ← 现在基本居中
光照：  正午强光 / 黄昏 / 阴影 / 逆光     ← 现在单一
个体：  不同锥桶、不同挡板、蓝底/红底赛道 ← 别只用同一个道具
负样本：无目标的纯赛道帧 ≥ 15%            ← 现在完全没有
```

### 2.3 各元素专项要求

| 元素 | 关键要求 |
|---|---|
| 红绿灯 | **录视频覆盖"灭→红→绿"完整周期**（灯控时序：灭5s→红5s→绿5s），按事件抽帧（切换瞬间前后 1s 内每 0.1s 抽 1 帧），过渡帧单独归档**不得丢**。每类 ≥400 实例；4 距离 × 4 光照 × 3 横向 ≈ 48 段素材。详见 `专项方案/红绿灯识别与通过方案.md` |
| 停车区 | 补拍 400~500 张、多片段多光照；必须包含**蓝板在左/在右、板压中线、板盖半格**等放法 |
| 锥桶 | 蓝锥/红锥分开；远距离小目标是召回难点 |

### 2.4 采集用文件夹组织

沿用现有约定：`train/project/<类别或场景名>/`，文件名保留原始时间戳（`frame_YYYYMMDD_HHMMSS_mmm_NNNN.jpg`），**这样切分时才能按片段分组**。⚠️ Roboflow 导出会重命名文件（`xxx_png.rf.<hash>.png`）导致片段信息丢失，**必须在本地保留一份原始文件名映射**。

## 3. 标注规范

| 项 | 要求 |
|---|---|
| 工具 | 检测框：LabelImg / Roboflow / Ultralytics；分割：X-AnyLabeling（内置 SAM，半自动）/ CVAT / Labelme |
| 导出格式 | Roboflow 选 **YOLO TXT (Detection)**；输出 `images/` + `labels/` + `data.yaml` |
| 红绿灯 | **框整个灯箱**（不是只框亮着的灯珠），所有帧边界一致；灭灯也要框得住 |
| 停车区 | 整个大黄框**一个实例一个框**；蓝板单独框 |
| 严重模糊/遮挡帧 | 不标，但单独存 `hard_cases/` 供复盘 |
| ⚠️ Roboflow 里**禁止**做 train/val/test 划分 | 它默认随机划分，会把连续帧拆散 → 验证集虚高 |

## 4. 切分规范

- **必须按拍摄片段整组切分**，严禁按图片随机切分（相邻帧几乎相同 → 验证集虚高、实车失效）；
- 比例建议 **8 : 1 : 1**；验证/测试集保持真实类别分布，不做人工平衡；测试集最好留**一整段独立录制**；
- 工具 `train/split_dataset.py`：`frame_*` 按 ISO 时间戳间隔 > `--gap-sec`(默认 10s) 分片段；非 frame 命名用 dHash 8×8 + 汉明距离聚类去重；整组只进 train/val/test 之一。
  - ⚠️ **它目前是给"图像分类"数据集用的**（一个类别一个文件夹），且**还没跑过**（`train/dataset` 不存在）。检测/分割的划分要么扩展它，要么另写一个只做"分组+划分"的脚本，直接产出 `images/labels` 结构。

## 5. 训练

### 5.1 环境

PC 训练环境（Windows + RTX 40 系）的**唯一权威说明在 `code/README.md`**，一键重建脚本 `code/setup_yolo_env.ps1`，自检脚本 `code/verify_yolo.py`（打印 python/torch/cuda/ultralytics 版本，并可用上届权重跑通推理链路）。
> 原 `doc/电脑端ultralytics环境搭建.md` 已被本文取代并删除——它写的 `.venv-ultra`、`dev/tools/requirements-vision.txt`、`dev/tools/verify_vision_model.py` 这些路径**都不存在**。

### 5.2 训练命令（YOLO11n-det）

```bash
yolo detect train \
  data=datasets/smartcar2026/data.yaml \
  model=yolo11n.pt \
  imgsz=640 epochs=300 patience=50 batch=16 device=0 \
  optimizer=AdamW lr0=0.001 lrf=0.01 warmup_epochs=3 weight_decay=0.0005 \
  mosaic=1.0 close_mosaic=15 mixup=0.1 \
  hsv_h=0.015 hsv_s=0.7 hsv_v=0.4 \
  degrees=5 translate=0.1 scale=0.5 shear=2.0 perspective=0.0 \
  fliplr=0.0 flipud=0.0 \
  cache=ram amp=True seed=0
```

- `fliplr=0.0`：类别表里已经没有左右语义了，原则上可以放开到 0.5，但**第一版建议先保持 0**，等基线出来再对比；
- 训练前 `yolo checks` 校验标签，并检查重复图片；
- 类别不平衡：**不按张数裁剪对齐**，优先补拍少数类；多数类按 `--stride 2~3` 抽帧降冗余。

### 5.3 验收标准

- mAP 达标（停车/红绿灯等关键类召回优先）；
- **特别关注误检**：竞速真正怕的不是帧率低，而是误检导致误刹车/误停车。

## 7. RKNN 转换（INT8）

### 7.1 为什么不用 Ultralytics 云平台的 rknn 导出

平台内部同样是 `pt → ONNX → RKNN`，但**云端模板无法指定校准集**——而 INT8 精度几乎完全由校准图片决定。所以走本地/服务器转换。

### 7.2 校准集

- 数量 **10~50 张**，来自**真实赛道场景**（可直接从 §2 的数据里挑）；
- 写 `dataset.txt`，**每行一张图片的绝对路径**；
- 注意：RKNN 量化时喂给模型的是**未做 letterbox 的原图**，校准图应尽量覆盖不同光照/距离。

### 7.3 转换

```bash
python convert_rknn.py --onnx best.onnx --output best_int8.rknn \
  --platform rk3588 --quantize --dataset dataset.txt
```

- 脚本：`dev/tools/convert_rknn.py`（参数 `--onnx/--output/--platform/--quantize/--dataset`），一键包装 `dev/tools/convert_rknn.sh`；
- **只能在 x86 Linux 上跑**（Windows 和板子上都不行）——服务器环境准备见 `远程连接与服务器手册.md` §6；
- ⚠️ 转换平台的 `rknn-toolkit2` 版本必须与小车端 `rknn-toolkit-lite2` 匹配，否则小车加载会失败。

### 7.4 精度对拍（必做）

- 同一批图分别跑 ONNX 和 RKNN，对比框/类别/置信度；
- 掉点严重 → 混合量化，或退回 FP16；
- 上板验证：`dev/vision/debug_view.py` 直接看画面与框。
