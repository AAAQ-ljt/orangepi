# 自动驾驶开发方案（按测试块推进）

> 建立 2026-09-16。按"分块测试"组织：**蓝板发车 → 块A(斑马线) → 块B(锥桶) → 块C(停车) → 操场实地**。
> 每块都能在台架/小场地独立验证，上一块不过不进下一块；**红绿灯本阶段不做**（代码占位、不触发）。

---

## 0. 总览

```text
① 模型适配层（让模型可插拔：上一届模型先测，我们模型好了只换配置）   ← 先做，半小时
② 蓝板发车检测加固（保证"一定识别到板"，覆盖两种放置时序）           ← 先做，1 小时
③ 块A：蓝板 + 斑马线（检测距离 → 减速停准 → 停 10s → 播报 → 继续）
④ 块B：蓝板 + 锥桶（S 走位绕两个锥桶，零触碰）
⑤ 块C：蓝板 + 停车（蓝板挡一侧 → 选另一侧 → 四轮入区）
⑥ 操场实地（现场标定 + 全链路）
```

三块都通过 → 上操场。每块都给：**涉及文件 / 场地怎么摆 / 怎么跑 / 通过标准 / 记录什么**。

## 1. 模型适配层（可插拔：换模型不改控制代码）

**问题**：现在 `vision/postprocess.py` 里写死了上一届的 9 个类 id（`left_lane/right_lane/zebra_crossing/…`），
我们自己的模型是 8 类检测（`crosswalk/parking_area/blue_board/…`）。类名一换，控制端就得跟着改——那不是解耦。

**做法**：把"模型输出"和"元素语义"分开。

```text
模型输出（per profile）        →   统一元素名（控制端只认这个）
zebra_crossing                →   zebra
obstacle_cone_blue / _yellow  →   cone          （颜色记在 color 字段）
parking_sign_A / parking_sign_B → parking_sign
crosswalk                     →   zebra
obstacle_cone_blue / _red     →   cone
parking_area                  →   parking_area
blue_board                    →   blue_board
traffic_light_off/red/green   →   light          （本阶段不用）
```

**新增/改动**
- 新增 `dev/config/model_profile.yaml`：两份 profile（`legacy` / `smartcar2026`），各写"类名 → 元素名"；
  另存 `nc`、输入尺寸、conf 阈值。
- 新增 `dev/vision/elements.py`：`Element(name, conf, xyxy, color=None, source=None)` +
  `parse_detections(outputs, profile)` → `List[Element]`（把后处理限定在这一层）。
- 改 `dev/vision/postprocess.py`：保留 NMS/解码，输出改为 `List[Element]`（不再有 `center_x=左右车道线均值` 这种旧逻辑）。
- 改 `dev/vision/vision_main.py`：加 `--profile legacy|smartcar2026`，把元素列表塞进 UDP 消息（新增 `elements` 字段）。
- 改 `dev/common/protocol.py`：新增 `elements`（列表，每项 `{name, conf, x1,y1,x2,y2, color}`），保持旧字段兼容。

**验收**：`python3 vision/vision_main.py --test-image 图.jpg --profile legacy`
打印出元素名列表（例如 `zebra 0.83, cone 0.61(color=blue)`），控制端不关心是哪个模型出的。

## 2. 蓝板发车检测加固（重点）

### 2.1 要覆盖的两种时序（都必须成立）

| 场景 | 期望行为 |
|---|---|
| **A. 程序启动前板已放好** | 启动后立刻确认"见到板"（日志/状态文件明确写出），**不动**；板被移走的瞬间起车 |
| **B. 程序启动后板才放上** | 启动后**绝不能动**；板放上后确认"见到板"；板被移走才起车 |

核心不变量（安全红线）：**"没见过板" 绝不放行**——先见板（连续 N 帧）→ 再见空（连续 M 帧）→ 才发车。

### 2.2 三路判据（融合，抗距离与光照）

| 判据 | 含义 | 为什么需要 |
|---|---|---|
| **① 最大蓝色连通域面积占比** | HSV 蓝掩膜 → 形态学去噪 → 取最大连通域面积 / ROI 面积 | 比"全 ROI 蓝像素占比"耐噪（排除零散蓝色杂物）；板远时占比小但连通域仍集中 |
| **② 蓝色主导度** | ROI 内 `mean(clip(B - max(R,G), 0, 255))` | 对光照/白平衡漂移比 HSV 硬阈值稳（曝光变了 HSV 会飘，通道差不会） |
| **③ 细节损失**（备选） | 拉普拉斯方差相对基线骤降 | 板贴到镜头前时画面大面积失焦；只在"贴脸"场景生效，默认关闭 |

判定：`有板 = ①超阈值` 或 `(②超阈值 且 ①过半阈值)`；③ 开启时作为附加条件。

### 2.3 状态机与操作员反馈

```text
WAIT_BOARD ──连续N帧有板──▶ ARMED ──连续M帧无板──▶ RELEASED(闩锁)
   │                                │
   └ 每 5s 打印一次"尚未见板（蓝占比 x% / 主导度 y）"  └ 立刻打印"已确认蓝板，等待移开"
```

- **见到板 → 打醒目日志 + 写状态文件**（这就是你要的"保证识别到板"的可验证证据）；
- **放行瞬间 → 打日志 +（可选）播一声短音**（`--gate-beep`），台架调试时不用盯屏幕；
- 超时（默认 90s）只见告警**不放行**；若一直没见到板，日志里会持续给数值，便于判断是"车没对准"还是"阈值不对"。

### 2.4 用哪路摄像头看板

板是**竖立**在车前 20~40cm、高 50cm；下摄（video2）朝地面，近距离可能只看到板底；云台摄（video0）朝前，能看到整块板。
→ `--gate-camera 0|2|both`，**默认 0（云台摄）**；`WAIT_START` 期间用它，**放行后切到行车摄像头（下摄）**跑巡线（双摄分时复用）。

### 2.5 台架测试（**一个脚本全包**：`dev/scripts/bench_test.py`）

```bash
# ① 只看读数不动电机
sudo python3 /root/dev/scripts/bench_test.py --no-motor

# ② 正式跑（一条命令到底）：板在→停 / 板移开→**低速对齐**→循迹 / 再见板→立即停
#   ★ 竞速里裁判不会给你"先标定再跑"的时间，所以车道中心由本命令在起步瞬间自动标定
sudo python3 /root/dev/scripts/bench_test.py --allow-motion --max-seconds 30

# ③ 只测蓝板+电调（不循迹、不对齐）
sudo python3 /root/dev/scripts/bench_test.py --no-lane --allow-motion

# ④ 观察转向（忽略"无有效车道"保护，仅台架用）
sudo python3 /root/dev/scripts/bench_test.py --force-run --no-motor

# ⑤ 只做静止标定（车不方便动、或想单独核对读数时用；平时不需要）
sudo python3 /root/dev/scripts/bench_test.py --calibrate 30
```

**边跑边标定（默认开）**：板移开、车还没动的那几帧就是最干净的标定样本——取 12 帧稳定的车道中心
（波动 ≤25px、数值在 120~540 内）直接当 `TARGET_X`，同时写进 `config/site.yaml`（以后所有程序自动读），
日志会打印 `🎯 边跑边标定：车道中心 = …（修正 +xx px）`。不可信就不改（继续用 site.yaml 里的值）。
想关掉：`--no-auto-target`。

> 为什么必须这样：摄像头是偏装的，车道中心在画面里**不是 320**（本车实测 407~422）。
> 标定值偏 15px ≈ 车会稳定偏 6cm 走——不会立刻翻车，但压线、停车入库都会跟着歪。

**起步对齐（针对"车不一定被摆正"）**：车是阿克曼、原地转不了向，所以对齐 = **低速蠕动 + 转向修正**：

```text
板移开 → 【ALIGN】电调 = --start-us（默认 1560，电调死区 1545 之上），转向由 PID 往车道中心修
       → |误差| ≤ --align-tol(15px) 连续 --align-frames(8) 帧 → 【TRACK】提速到 --speed-us(1575)
       → 对齐超时 --align-max-s(6s) 也提速（避免原地磨蹭）
       → 对齐期间连续 3s 没有有效车道 → 按保护停车并提示重新摆放（不盲目前冲）
       → 对齐结束时打印**转向方向判定**（误差 26px→7px 收敛 = 方向对；越修越大 = steer_sign 反了）
```

**电调死区（2026-09-16 架空实测）**：1500us 停、**1540us 轮子仍不转、≈1545us 才起转**。
所以任何"要让车动"的脉宽都必须 > 1545：默认起步 1560 / 循迹 1575；调试上限 `ESC_DEBUG_MAX_US=1600`
（约 20% 行程）。命令行给了低于死区的值会被脚本**直接拒绝**（并把实测值打印出来），避免再白跑一次台架。

**安全优先级（有单测）**：没见板 → 中位；**板在 → 中位（即使 `--force-run`）**；无有效车道 → 中位；
未对准 → 起步脉宽；对准 → 循迹脉宽。

> ⚠️ "板放回就停"这个行为**只存在于台架脚本**：比赛里发车后再看到蓝板是正常的
> （停车区的挡板就是同一块蓝板），主程序若按这个规则跑，会在停车区前自己停下。

**用哪路摄像头**：台架脚本默认**单摄 `--camera 2`（下摄）**，蓝板与扫线都用它（实测板在车前时下摄也看得到：面积 0.638），不需要切换。
主程序 `vision_main.py` 是另一套：发车阶段用云台主摄（`--gate-camera 0`）看板，放行后切下摄跑巡线。

**读数参考（2026-09-16 车上实测，板放在车头前）**：

| 摄像头 | 面积占比 | 主导度 | 判据 | 阈值余量 |
|---|---|---|---|---|
| `--camera 0` 云台主摄 | **0.769** | **93.2** | 两路都远超 | 12× / 2.7× |
| `--camera 2` 下摄（台架默认） | **0.638** | 24.9 | **靠面积判据**（主导度 25 < 35） | 10× |

结论：**两路都能稳定识别到板**，阈值不需要现场标定（`START_BLUE_AREA_THRESH=0.06` / `START_BLUE_DOMINANCE_THRESH=35` 已很宽裕）。
第二行也正好说明"双判据取或"的价值——下摄看到的板偏"洗白"，色差判据不够，全靠面积判据兜住。

> 台架上如果镜头对着空旷处，扫线读数没有意义（置信度低），这是**正常的**——
> 它说明"无有效车道"保护在工作；要观察转向响应可用 `--force-run`。

## 3. 块 A：蓝板 + 斑马线

**目标**：发车 → 巡线 → 在斑马线前**停在距横道边缘 30cm 内** → 停满 10 秒（期间播报）→ 继续巡线。

| 项 | 内容 |
|---|---|
| 涉及文件 | `vision/elements.py`（zebra 元素）、**新增** `vision/distance.py`（接地线→距离）、**新增** `control/approach.py`（减速停准）、`control/fsm.py`（`ZEBRA_STOP` 细化） |
| 场地 | 一小段直道（≥10m）；斑马线用打印/白纸条按规则摆（中间那条压赛道中心线）；车头对准中线 |
| 怎么跑 | `bash /root/dev/scripts/car-mode.sh auto --real`（默认用下摄巡线 + 云台摄看板） |
| 通过标准 | 连续 **5 次**：停车点距横道边缘 30cm 内、停满 10s、播报正常、起步后不压线 |
| 记录 | 每次停车距离（卷尺量）、停顿时长、播报是否清晰 |

**距离估计（这块的关键）**：`distance.py` 用**离线标定表**——把车摆在距目标 1/2/3/5/8m 处，
记录检测框底边 y 值，拟合 `d = k/(y - y0)`，存进 `config/ground_map.yaml`；运行期查表插值（IPM 是后续精化的选项）。
**减速停准**：`approach.py` 按"当前距离 + 目标停车距离"给出油门比例，临近时松油门 + 短促反脉冲刹住；目标是停稳不点头。

## 4. 块 B：蓝板 + 锥桶（S 走位）

**目标**：发车 → 巡线 → 用 S 走位绕过**固定在跑道中间**的两个锥桶（间距先按 2.5m）→ 回到中线继续。

| 项 | 内容 |
|---|---|
| 涉及文件 | **新增** `control/avoid.py`（绕障横向偏移控制）、`control/fsm.py`（`AVOID_CONE` 从"降速"改为"走位"） |
| 场地 | 直道，两锥桶固定在赛道中间、间距 2.5m（按规则 ≤3m）；车从 5m 外出发 |
| 怎么跑 | 同块A；`--real`，绕行段自动限速 |
| 通过标准 | 连续 **5 次**：锥桶零触碰（锥桶原地不动）、不压线、S 走位完整（左-右 或 右-左） |
| 记录 | 每次用时、是否触碰、最大横向偏移（可从状态文件里看） |

**算法（不写死固定时间序列）**：
```text
每帧：检测锥桶 → 取最近的那个
  距离 < 4m 且 尚未让位 → 判定锥桶在"车道中心"的左/右 → 目标横向偏移 = 往反方向让 25~35cm
  通过判据：该锥桶距离 > 2m 或 消失 → 反向切换偏移（为第二个锥桶让位）
  两个都过 → 偏移归零，回到中线
实现：目标 = 车道中心 + 偏移 → 直接喂给现有 PID（不重写控制）；绕行段限速 60%，
     横向偏移变化率限幅（复用转向 slew），避免画龙
```
> 开发期固定摆位能调通，但**方向必须由检测决定**——比赛时锥桶靠左/居中/靠右是随机的。

## 5. 块 C：蓝板 + 停车

**目标**：识别停车区（黄胶布框 + 蓝板挡一侧）→ 判定哪半格空着 → 低速入库 → **四轮入区**停下。

| 项 | 内容 |
|---|---|
| 涉及文件 | **新增** `vision/parking.py`（HSV 蓝板 + 黄线 + IPM 俯视 + 左右判定）、**新增** `control/parking_fsm.py`（五阶段） |
| 场地 | 按规则摆黄胶布（1m×赛道宽、中线分隔）+ 蓝板挡任意一侧；先静止标定，再动态跑 |
| 怎么跑 | 同块A |
| 通过标准 | 连续 **5 次**：四轮全部在黄框内、不撞蓝板；左右两侧遮挡各测 3 次 |
| 记录 | 最终车位（左/右）、四轮与黄线的关系（拍照留档） |

**为什么这块不依赖模型**：蓝板（纯蓝大色块）和黄胶布（纯黄）用 HSV + 形态学就足够稳，
模型只作为后续的二次校验 → **现在就能开工**，不受标注进度影响。
**标定**：把车停在停车区前 3m，用地上已知矩形（黄框）标定 IPM 单应矩阵，参数写进 `config/parking_map.yaml`（摄像头固定，标一次即可）。

## 8. 红绿灯（本阶段占位）

- `fsm.py` 保留 `TRAFFIC_LIGHT` 状态与转移，但**触发入口不接**（无光电、无云台抬头逻辑）；
- `elements.py` 里保留 `light` 元素名，`model_profile.yaml` 中 `smartcar2026` 已写三类灯态，
  但**本阶段不消费**；
- 代码区留 `# TODO(P-light)` 注释，等光敏传感器到位 + 云台标定后再实现。
